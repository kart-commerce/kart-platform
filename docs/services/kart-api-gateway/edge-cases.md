# Edge Cases: kart-api-gateway

## Edge Case: Upstream service down or circuit-open

- **What happens:** A request routed to `kart-identity-service` or `kart-category-service` (or a future service) arrives at the Gateway, but the upstream is unreachable, timing out, or returning 5xx at a sustained rate.
- **Why it happens:** The Gateway is a proxy, not the owner of upstream availability (requirement-spec §1/§2) — one backend's outage must not become the Gateway's own outage for every other route, since the Gateway sits on the critical path of every request platform-wide (requirement-spec §3, 99.99% tier).
- **Solutions available (3):** No isolation — let a slow/failing upstream block the Gateway's own thread/connection pool until the client-side timeout fires · Per-cluster circuit breaker + bounded timeout, isolated per upstream service, so one service's outage degrades only its own routes · Retry indefinitely against the failing upstream, hiding the failure from the client at the cost of amplifying load on an already-struggling service.
- **Decision (4 bullets):**
  - Chosen: Per-cluster (per-upstream-service) circuit breaker with an explicit connect/request timeout budget, matching the platform's own general resilience default (`PLATFORM_BLUEPRINT.md`'s resilience standard, already applied identically by `kart-shipping-service`'s carrier-API breaker and `kart-recommendation-service`'s fail-open dependency calls) — YARP's `HttpClientConfig`/active-health-check + destination-level circuit breaking mechanism (`design-decisions.md`).
  - Why: isolating the breaker per upstream cluster is what keeps `kart-identity-service` being down from also blocking traffic to `kart-category-service` — the two share nothing but the Gateway process, and the Gateway's own 99.99% target (requirement-spec §3) must not inherit the lower availability tier (99.9%, secondary path) of a service like Category.
  - Trade-off accepted: a client calling a route whose upstream is circuit-open gets a fast, explicit 502/503 rather than a slow timeout — a strictly better failure mode, but it does mean the Gateway must return a client-facing error for that route rather than silently retrying or degrading gracefully to a cached response (no cached-fallback content exists for auth/category writes, so none is invented here).
  - No retry-with-backoff against a circuit-open upstream is implemented at the Gateway for non-idempotent routes (e.g. `POST /v1/categories`) — retrying a write that may have already partially succeeded upstream is a correctness risk the Gateway cannot resolve without an idempotency key, which is Category's own concern (its `api-contract.yaml` notes idempotency is "not applicable" for its non-money-moving writes) — not invented here as new Gateway scope.

## Edge Case: JWT validation failure modes

- **What happens:** A request presents a bearer token that fails validation for one of several distinct reasons: missing/malformed header, expired token, signature that doesn't verify against any key in the cached JWKS document, or a `kid` in the token header that isn't present in the cached key set at all (e.g. Identity rotated signing keys since the Gateway's cache was last refreshed).
- **Why it happens:** The Gateway validates JWTs statelessly at the edge against a cached public key (requirement-spec §2, reusing `kart-category-service`'s `JwksSigningKeyResolver.cs` pattern) — a 10-minute cache window (the same duration already chosen by that resolver) means a just-rotated key can be legitimately absent from the cache for up to that window.
- **Solutions available (3):** Treat every validation failure identically (401, generic message) regardless of cause · Distinguish "no token supplied" (401, route requires auth) from "token present but invalid/expired/unknown-kid" (401, distinct reason code) but never force a synchronous JWKS re-fetch mid-request · On an unknown-`kid` specifically, force an immediate synchronous re-fetch of the JWKS document before failing the request, to self-heal within the same request rather than waiting out the cache TTL.
- **Decision (4 bullets):**
  - Chosen: Distinguish failure causes in the response body's `code` field (`missing_token`, `token_expired`, `invalid_signature`, `unknown_signing_key`) for client/observability clarity, all returned as HTTP 401 — but do **not** force a synchronous re-fetch on an unknown-`kid` miss; the existing 10-minute cache refresh (already an accepted trade-off in `kart-category-service`'s own resolver) is reused unchanged.
  - Why: reusing the exact same resolver/cache-duration `kart-category-service` already has approved and shipped keeps the Gateway consistent with every downstream service's own JWKS-consumption behavior (requirement-spec §2) rather than introducing a second, gateway-specific key-rotation-handling policy; a synchronous re-fetch-on-miss would also reintroduce a per-request round-trip to Identity on every rotation window, which is exactly what the cached-key design exists to avoid (`kart-identity-service/architecture.md`: "cached and infrequent — not a per-request round trip").
  - Trade-off accepted: for up to 10 minutes after Identity rotates its signing key, a token signed with the new key can be rejected by the Gateway's stale cache even though it is genuinely valid — a bounded, known window, not an open-ended one, and no worse than the equivalent window already accepted by `kart-category-service`'s identical mechanism.
  - Distinct response codes (vs. one generic 401) cost nothing extra to implement and materially help debugging a client integration issue — this is a low-cost addition to what the BRD/requirement-spec asks for, not scope invention, since "JWT validated at gateway edge" (BRD §18) implies *some* rejection response, and a single undifferentiated 401 would be a worse implementation of the same stated requirement.

## Edge Case: Rate-limit exceeded

- **What happens:** A caller (anonymous IP, authenticated user, or Partner API client) exceeds the token-bucket limit for their tier on a given route.
- **Why it happens:** BRD §18 mandates tiered token-bucket rate limiting; any bucket-based limiter has a bucket-exhausted state by construction, and the platform's flash-sale traffic profile (BRD §4.2's 10,000,000 RPM Extreme tier) makes hitting that state a routine, expected event, not a rare one.
- **Solutions available (3):** Silently drop the request (no response) · Return HTTP 429 with a `Retry-After` header computed from the bucket's own refill rate · Queue the request until a token becomes available, rather than rejecting it.
- **Decision (4 bullets):**
  - Chosen: HTTP 429 with a `Retry-After` header (seconds until at least one token is available), using ASP.NET Core's built-in rate-limiting middleware's own `OnRejected` callback to compute it from the same token-bucket options the limiter is already configured with (`design-decisions.md`).
  - Why: silently dropping breaks HTTP semantics and every client-side retry heuristic that inspects status codes; queuing turns a fast-fail edge protection mechanism into a second, unbounded queuing layer in front of every upstream service — exactly the "distributed monolith" queuing risk the platform's resilience standard warns against, and it defeats the reason rate limiting exists at the edge in the first place (protecting upstream capacity, not delaying overload).
  - Trade-off accepted: a legitimate burst from a single well-behaved client (e.g. a page load firing several near-simultaneous requests) can trip the same 429 an abusive client would — the per-tier bucket sizes in `design-decisions.md` are chosen generously enough that a normal client interaction pattern does not routinely hit this, but it is not impossible by construction.
  - The 429 response is deliberately excluded from the request-size/JSON-body-parsing pipeline (returned before the body is read) so an oversized or slow request body cannot itself contribute to the resource cost of a rate-limit rejection.

## Edge Case: Request larger than a size limit

- **What happens:** A client sends a request whose body exceeds a configured maximum size.
- **Why it happens:** Nothing in the BRD's per-route contracts (Identity's auth payloads, Category's taxonomy CRUD payloads) needs a large body — an oversized body on any of today's routes is either a misbehaving client or an attempted resource-exhaustion probe, and forwarding it to an upstream service wastes that service's own memory/bandwidth budget on a request that was always going to be rejected.
- **Solutions available (3):** No limit — rely on each upstream service's own body-size handling · A single platform-wide limit applied uniformly at the Gateway, rejecting oversized requests before they are proxied · A per-route limit, since different routes have legitimately different expected payload shapes (e.g. a future bulk-catalog-upload route vs. a `PATCH /v1/categories/{id}` rename).
- **Decision (4 bullets):**
  - Chosen: A single platform-wide default limit (1 MB) applied at the Gateway via ASP.NET Core's request body size limit, with the explicit provision that a future route needing a larger payload (e.g. Partner API bulk upload, out of scope for this release) overrides it per-route rather than raising the global default.
  - Why: every route that exists in this release (auth payloads, category CRUD payloads) is comfortably under 1 MB — `kart-identity-service`'s and `kart-category-service`'s own `api-contract.yaml` request bodies are all small, flat JSON objects, so 1 MB is generous headroom, not a tight fit that risks false rejections; rejecting at the edge protects both services' own request-parsing/validation cost from ever seeing an oversized payload.
  - Trade-off accepted: this number is an engineering default, not a BRD-stated figure — flagged explicitly here rather than silently assumed, per `AGENTS.md`'s rule; it will need revisiting the moment a route with a legitimately larger payload (e.g. bulk import) is added, which is why the decision is stated as "per-route override," not a single immutable global.
  - Rejected requests return HTTP 413 before any proxying, JWT validation, or rate-limiter accounting occurs against that request — an oversized body is the cheapest possible rejection and is checked first in the middleware pipeline (`design-decisions.md`).

## Edge Case: Redis revocation-check unavailable

- **What happens:** The shared Redis deployment backing `identity:revocation:*` (`kart-identity-service/architecture.md`'s Dependencies table) is unreachable or timing out when the Gateway attempts its per-request revocation check.
- **Why it happens:** The revocation check is a hard per-request dependency the moment a request carries a validated JWT (requirement-spec §2) — Redis becoming unavailable removes the Gateway's only mechanism for catching a revoked-but-unexpired token, the exact gap `kart-identity-service/edge-cases.md`'s "Stale Revocation Under Stateless JWT Validation" already names and already accepts a *bounded* (access-token-TTL-sized) window for under normal operation.
- **Solutions available (2):** Fail open — if the Redis check cannot complete, treat the token as not-revoked and let the request through, since JWT signature/expiry validation already passed · Fail closed — if the Redis check cannot complete, reject the request (503), treating "cannot confirm not-revoked" as equivalent to "possibly revoked."
- **Decision (4 bullets):**
  - Chosen: Fail closed (reject with 503) if the revocation-check Redis call errors or exceeds a short timeout, distinct from the normal 401-for-genuinely-revoked-token response.
  - Why: `kart-identity-service/edge-cases.md`'s own accepted trade-off is a *bounded, known* stale-revocation window sized to the ~15-minute access-token TTL — failing open on an infrastructure outage would silently widen that window for the outage's entire duration (which could be arbitrarily longer than 15 minutes), turning an accepted, bounded risk into an unbounded one the same ADR/edge-case never signed off on. A logged-out or admin-locked user's still-unexpired token must not become fully unrevocable just because Redis is briefly down.
  - Trade-off accepted: a Redis outage now also takes down every authenticated route platform-wide (503, not just the revocation guarantee weakening) — this is the direct cost of treating the check as load-bearing rather than best-effort, and it is the reason `kart-identity-service/architecture.md`'s Redundancy section already commits to deploying this Redis cluster at the same 99.99% HA posture as Identity itself ("Redis is no longer 'only' Identity's dependency ... its availability posture must not be the weakest link"). The Gateway does not need a second HA design for this Redis — it inherits the one Identity's own architecture doc already committed to.
  - Anonymous/unauthenticated routes (e.g. `GET /v1/categories`) are entirely unaffected by a Redis outage — the revocation check only ever runs for requests bearing a validated JWT, so read-only public traffic keeps flowing even if Redis is down.
