# Design Decisions: kart-web

Cross-cutting technology/design-pattern choices forced by this app's requirement-spec and edge-cases. Service/architecture boundaries (Gateway-only access, no direct backend calls), the domain model, and schema design are already decided (`architecture.md`) and out of scope here.

## Decision: Cross-Tab State Synchronization — Split by Concern

- **Requirement driving this:** Domain/UX Invariant #1 (`requirement-spec.md` §8: cart never invents client-only state diverging from the server); `security.md` §2.1's `BroadcastChannel('kart-session')` multi-tab logout behavior; `architecture.md`'s Real-Time Integration (one WS/SSE connection per session multiplexing cart-sync/inventory/price/order-tracking); edge-cases.md's "GDPR Erasure Submitted While an Authenticated Session Is Open in Another Tab" (reuses the session broadcast for erasure).
- **Options considered (3):** one `BroadcastChannel` carrying both session-control events (login/logout/erasure) and domain-data events (cart/price/stock changes) · two mechanisms split by concern — `BroadcastChannel` for local, same-device, tab-to-tab session-control signals, and the existing single WS/SSE connection to the Gateway for server-authoritative domain-data push · rely solely on the WS/SSE connection for everything, with no local tab-to-tab channel at all.
- **Decision:**
  - Chosen: two distinct mechanisms split strictly by concern — `BroadcastChannel('kart-session')` for local, instant, same-device session-control events (login, logout, GDPR erasure) with no server round-trip; the existing single WS/SSE connection per session (`architecture.md`) for server-authoritative domain data (cart, price, stock, order/delivery status), each tab independently subscribing.
  - Why: these solve two different problems with two different authorities — session-control's authority is "did the user, right here, on this device, just log out," answerable instantly without a server round-trip, while cart/price/stock/order state's authority is always the server (Invariant #1) and must go through the one real connection per session; collapsing them would either force logout through an avoidable WS round-trip or force domain-data sync into a same-device-only channel a second device could never receive.
  - Trade-off accepted: two mechanisms to reason about instead of one unified pub/sub abstraction — justified because the GDPR erasure edge case specifically reuses the session channel *because* it already "closes every other authenticated tab instantly," proving the split answers genuinely different latency/scope needs, not an arbitrary one.

## Decision: TransferState Trust Boundary (Hydration Staleness Policy)

- **Requirement driving this:** `seo.md` §10's TransferState rule (excludes only live price/stock); Domain Invariants #2/#4 (`requirement-spec.md` §8); edge-cases.md's "SSR-Rendered Price/Stock Hydration Mismatch Against a Live Update Arriving Mid-Hydration" (final) and "Deferred-Hydration Widget Consuming a TransferState Value Aged Out Before Its Trigger Fires" (resolved, client-tier default).
- **Options considered (3):** keep `seo.md` §10's original narrow exclusion (live price/stock only), trusting every other TransferState payload — including `@defer`-gated widgets — indefinitely · generalize to a "staleness by time-to-use" rule: any TransferState payload whose point of use is deliberately decoupled in time from its SSR fetch (deferred hydration triggers, or the gap between SSR flush and real-time reconnect) is never trusted and is re-fetched fresh at the point of use, while payloads consumed immediately at hydration keep TransferState's benefit · attach a uniform numeric max-age to every TransferState payload platform-wide, regardless of data type.
- **Decision:**
  - Chosen: the generalized "staleness by time-to-use" rule — TransferState is trusted only for data consumed the instant hydration completes with no further delay (name/images/description); live price/stock re-fetch authoritatively the moment hydration completes (first edge case), and every `@defer`-gated widget (recommendations, reviews, promos) re-fetches fresh at its actual trigger time rather than reusing its SSR-time payload (second edge case).
  - Why: both edge cases independently converge on the same underlying principle instead of two unrelated fixes — naming it once here avoids re-deriving it ad hoc for the next data type with the same time-decoupling problem; a uniform numeric max-age (option 3) has no spec'd number to anchor to and would be either too aggressive for immediate-use content or too lax for a widget genuinely deferred a long time.
  - Trade-off accepted: gives up TransferState's no-second-fetch benefit for a wider set of data than `seo.md` §10 originally named — bounded in practice to non-LCP-critical content, since anything LCP-critical hydrates immediately and stays on the fast path.

## Decision: Locale-in-URL-Path vs. Currency-Outside-URL (Resolution/Routing Strategy)

- **Requirement driving this:** `requirement-spec.md` §2 (i18n row) and §9 resolution #1; `localization.md` §2 (locale resolution order, URL segment as the stable CDN cache key) and its Currency Decision Set (currency as an independent, non-URL axis); `architecture.md`'s CDN-first, SSR-per-request posture.
- **Options considered (3):** encode both locale and currency in the URL path (e.g. `/en-USD/...`) so both are equally cacheable CDN keys · resolve locale via a URL path segment (cacheable, crawlable, canonical) but resolve currency purely via cookie/account-field/geo-header with no URL encoding, since currency is an independent, non-SEO axis · resolve both purely via cookie/`Accept-Language`/geo-header, with no URL encoding for either.
- **Decision:**
  - Chosen: locale is a first-class URL path segment (`/en/`, `/bn/`, `/de/`), resolved server-side before the first byte; currency is resolved independently via cookie/account-field/geo-header with no URL encoding, triggering a synchronous client-side re-quote on switch rather than a navigation.
  - Why: locale changes served content/meta/structured-data — a crawl-relevant, per-URL-cacheable concern, and `localization.md`'s own stated reason a cookie-only locale would fragment CDN cache entries — while currency only changes a displayed number via an already-server-owned `/pricing/quote` call with no distinct content or SEO implication; encoding currency in the URL would multiply the CDN's cacheable-URL space (locale × currency) for a value that isn't crawl-relevant at all, contradicting `localization.md`'s explicit locale/currency-orthogonality design.
  - Trade-off accepted: currency is never part of a shareable/bookmarkable canonical URL — a shared link carries the sender's locale but never their currency choice, a deliberate asymmetry since currency is a personal display preference, not page content.

## Decision: Idempotency-Key Generation & Lifecycle (Client-Side)

- **Requirement driving this:** `requirement-spec.md` §3.4 (client generates/attaches `Idempotency-Key` on every money-moving action, submit disabled until a definitive response); `checkout-and-refunds.md` §A.2 (key persisted "for the duration of the checkout attempt," extended to `POST /orders/{id}/return-request`); BRD §24's platform-wide mandatory idempotency-key rule, the same client-supplied-header pattern `kart-order-service/design-decisions.md` already establishes backend-side.
- **Options considered (3):** one UUID v4 per distinct user-initiated attempt (generated at submit intent, held in memory/component state only for that attempt's lifetime including automatic retries, discarded on a definitive response) · one key generated once per checkout session, reused across every retry and every logically-distinct submission within that session · defer key generation to the HTTP interceptor layer, transparently attaching a key to any money-moving-route POST with no feature-level awareness of its lifecycle.
- **Decision:**
  - Chosen: one UUID v4 per distinct user-initiated attempt, generated at submit intent, held only in that attempt's in-memory/component state (never `localStorage`/`sessionStorage`, consistent with `security.md` §1's token-storage prohibition), reused automatically for network-layer retries of that same attempt, discarded the instant a definitive response arrives — a subsequent distinct attempt (e.g., cart edited and resubmitted) always gets a new key.
  - Why: the key's purpose is deduplicating retries of the *same* logical attempt (double-click, network retry) — a session-scoped key (option 2) risks a genuinely new request (e.g., resubmit with a different payment method after a decline) colliding with a stale key and being wrongly deduplicated by the backend's unique-constraint guard.
  - Trade-off accepted: the feature layer (checkout, return-request) must own key generation/disposal itself rather than a fully-transparent interceptor (option 3), since only the feature knows when one logical attempt ends and a new one begins.

## Decision: Return-Request Auto-Approval Gate — Business-Rule Placement

- **Requirement driving this:** `checkout-and-refunds.md` §B.4/§B.9 (auto-approval eligibility thresholds — amount, prior-return count, payment-rail — stated to be "the fraud gate," "server-evaluated"); edge-cases.md's "Self-Service Return Auto-Approval Racing a Chargeback on the Same Order" (resolved, final); `architecture.md`'s Boundary Rationale ("every client-side check is UX convenience, never the actual boundary").
- **Options considered (3):** client precomputes and displays an "auto-approval eligible" indicator from its own cached order/customer data before submission · client performs no eligibility computation or pre-submission check at all, submitting blind and rendering whatever the server ultimately returns · client performs a narrow, single-purpose fresh-state check immediately before submission (re-fetch `GET /orders/{id}`, block only on an already-`Refunded`/dispute-flagged order) while all eligibility/fraud-gate logic stays entirely server-evaluated, re-checked at submission time regardless of what the client last saw.
- **Decision:**
  - Chosen: the narrow fresh-state check (option 3) layered on top of — never substituting for — the fully server-owned eligibility/fraud gate; the client never computes or displays "you qualify for instant approval" ahead of actual submission.
  - Why: the gate's own inputs (rolling 90-day repeat-return count, chargeback/dispute state) are exactly what `checkout-and-refunds.md` §B.9 keeps server-side so thresholds stay "tightenable later without any client-code change" — a client-side precomputation would duplicate that logic and go stale the instant a chargeback lands in the same window the edge case describes; the fresh-state re-fetch is kept solely because it improves the common-case UX (a specific message instead of a raw error), never as a substitute for the actual gate.
  - Trade-off accepted: a customer who appears to qualify by every visible signal can still be routed to manual review or rejected at submission with no advance client-visible warning (e.g., an invisible repeat-return count crossing the threshold) — an intentional consequence of keeping fraud-relevant logic entirely opaque to the client, not a bug.

## Decision: Cookie-Consent Staleness Check Granularity

- **Requirement driving this:** `privacy.md` §A.4 ("stale" consent re-shows the banner "on next visit"); edge-cases.md's "Cookie-Consent-Version Bump Arriving Mid-Session With Analytics Already Loaded" (resolved as a client-tier default).
- **Options considered (3):** check `consentVersion` only at a fresh SSR page load, per `privacy.md`'s literal wording · check on every Angular Router client-side navigation (`NavigationEnd`), re-showing the banner in-session the moment a version mismatch is detected, no reload required · push the new `consentVersion` over the existing real-time WS/SSE connection as a new message type, forcing an immediate in-session check with no navigation needed.
- **Decision:**
  - Chosen: check on every client-side route navigation (`NavigationEnd`), reusing the already-fetched consent-config value rather than issuing a new fetch per check.
  - Why: closes the materially long exposure window a literal "next visit" would leave open for a long-lived SPA session, at near-zero cost — reuses a router event Angular already fires and a config value already loaded at boot — without inventing a new real-time message type for a non-domain concern the real-time channel is never otherwise used for.
  - Trade-off accepted: a single-page session with no further in-app navigation (e.g., one PDP visit ending in tab-close) still won't see the updated banner until the next visit — narrows, but doesn't fully close, the gap; fully closing it would require the real-time-push option this decision explicitly declines to build for a non-domain, non-money concern.

## Decision: Feature-Flag Resolution Timing & Lifecycle Management

- **Requirement driving this:** `api-strategy.md` §4/§8 (Unleash, four-stage Mocked → Contract-Tested → Staged → GA lifecycle; a flag deleted the same/next sprint after 100% Production rollout); edge-cases.md's "Feature Flag Flips ON in Production While a Tab Is Already Open With Old Cached Code" (final).
- **Options considered (3):** resolve every flag's value once per SSR bootstrap/session and never re-check it client-side for that tab's lifetime, deferring any flip's visible effect to the tab's next navigation-triggered SSR response or full reload · poll the flag-evaluation endpoint (or push over the existing real-time channel) and hot-swap feature availability mid-session, including dynamically importing a previously-unloaded feature module · force a one-time hard reload of any open tab the instant a relevant flag flips, pushed over the real-time channel.
- **Decision:**
  - Chosen: resolve once per SSR bootstrap/session (option 1), combined with `api-strategy.md`'s existing discipline that a flag is deleted the same/next sprint once its guarded feature reaches 100% Production rollout, so no flag lives long enough for "stale open tab" exposure to compound across releases.
  - Why: matches this app's existing SSR-then-long-lived-client-routing architecture directly, and a GA flip is already the end of a soak/rollout process (`api-strategy.md`'s own four-stage model), not an instant customer-facing cutover needing sub-session precision; options 2/3 both require new infrastructure (a flag-push channel, dynamic module loading for a never-bundled module) this doc set establishes nowhere else, for a feature category that carries no correctness/money risk — unlike the real-time channels reserved specifically for cart/price/stock/order data because Domain Invariant #2 demands that precision there.
  - Trade-off accepted: two open tabs of the same session can show inconsistent feature availability for as long as the older tab stays open without navigating — acceptable specifically because it's scoped to non-critical feature-availability, never to the domain data this platform holds to a materially tighter real-time bar.

## Decision: Concurrency Control for Competing Async Client Reads

- **Requirement driving this:** Domain Invariant #1 (cart never invents client-only state diverging from the server) and #2 (price never staler than the mandatory checkout re-quote); edge-cases.md's "Currency Switch Mid-Checkout Racing the Mandatory Re-Quote" (resolved, client-tier default) and "Guest-Cart Merge Racing a Real-Time Inventory/Price Push" (final).
- **Options considered (3):** a single uniform "last response wins" policy for every concurrent client read, with no cancellation or buffering · a single uniform cancellation-token/request-generation policy applied everywhere a new read could supersede an in-flight one, canceling the older request outright · two purpose-fit mechanisms — cancellation-token-based race resolution when a new user-initiated action supersedes an in-flight read the user no longer needs (currency switch vs. step-entry re-quote), and suppress-and-buffer-then-reconcile when a one-time authoritative call is in flight and a separately-arriving push event could reference item identities about to change (guest-cart merge vs. real-time inventory/price push).
- **Decision:**
  - Chosen: two purpose-fit mechanisms (option 3) — a currency switch cancels any in-flight step-entry quote and the current checkout step re-validates fresh under the new currency; real-time cart-affecting events are suppressed/buffered during the guest-cart merge call's in-flight window and reconciled from the merge response once it returns, before normal event consumption resumes.
  - Why: the two races have different shapes — currency-switch is "the user changed their mind, the in-flight result is now meaningless" (a genuine supersession, cancellation is correct), while merge is "one call is about to become the sole source of truth for item identities a concurrent push event might reference by an id that's about to change" (a temporary authority takeover, buffering is correct since the push event isn't wrong, just possibly stale relative to a restructuring the merge itself causes); one uniform policy (options 1/2) would either leave a "last response wins" race exactly where Invariant #2 forbids it, or wrongly cancel a legitimate concurrent push event a currency-style cancellation was never meant to touch.
  - Trade-off accepted: two named mechanisms to maintain instead of one uniform race-resolution rule — accepted because the two edge cases genuinely differ in what the concurrent "other thing" represents (a superseded stale request vs. a legitimately-arriving event around a temporarily-authoritative call), not an invented distinction.
