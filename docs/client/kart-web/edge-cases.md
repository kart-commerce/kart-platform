# Edge Cases: kart-web

## Edge Case: SSR-Rendered Price/Stock Hydration Mismatch Against a Live Update Arriving Mid-Hydration

- **What happens:** a PDP/PLP is SSR'd with a price/stock value fetched at request time; a `ProductPriceChanged`/`InventoryReleased` push arrives over the real-time channel in the window between the SSR HTML being flushed and the client's real-time connection manager actually reconnecting (subscriptions establish post-hydration) — the customer briefly sees and can act on a value already superseded.
- **Why it happens:** `seo.md` §9/§10 explicitly excludes live price/stock from TransferState reuse and says they "re-fetch/re-subscribe immediately post-hydration," but "immediately post-hydration" still leaves a gap between SSR flush and the single WS/SSE connection (`architecture.md`'s Real-Time Integration section) actually being live — and Domain Invariant #4 (`requirement-spec.md` §8) forbids ever showing "in stock" once the backend has signaled otherwise.
- **Solutions available (3):** force an authoritative re-fetch (not merely re-subscribe) of price/stock as the very first client action on hydration-complete, discarding trust in the transferred value for these two fields only · embed a monotonic version/timestamp with the transferred price/stock and have the real-time connection manager replay any events since that timestamp once connected (event-catch-up) · accept the gap as bounded, relying on the checkout-time re-quote (Domain Invariant #2) as the real backstop and treating PDP-level staleness as cosmetic.
- **Decision (3-5 bullets max):**
  - Chosen: explicit re-fetch of price/stock the instant hydration completes, discarding the transferred value's trust for those two fields; TransferState is kept for the rest of the page payload (name/images/description) to preserve its no-second-fetch benefit elsewhere.
  - Why: this is a stricter reading of `seo.md` §10's own existing exclusion, not new infrastructure — it closes the gap without inventing event-catch-up machinery (option 2) that nothing else in this doc set specifies.
  - Trade-off accepted: one extra request per PDP/PLP load at hydration time, versus leaving a race window open.
  - **Status: final.** A tightening of `seo.md` §10, not a new mechanism requiring backend change — worth folding this wording back into `seo.md` §10 in a future revision for consistency.

## Edge Case: Currency Switch Mid-Checkout Racing the Mandatory Re-Quote

- **What happens:** a customer mid-checkout switches currency via the header's independent currency selector; `localization.md`'s "immediate, synchronous re-quote" trigger and `checkout-and-refunds.md` A.1's "every step re-validates on entry" trigger can both fire `/pricing/quote` concurrently, with no documented sequencing rule for which response wins or when currency-restricted payment-method narrowing (`localization.md`, Checkout Currency Behavior) should apply.
- **Why it happens:** the two re-quote triggers were specified in two different documents, each correct in isolation, but neither references the other's concurrent existence — both target the same endpoint from the same checkout session at possibly the same instant.
- **Solutions available (3):** cancellation-token/request-generation approach — a currency switch invalidates any in-flight step-entry re-quote, and the current step re-validates fresh under the new currency · block the currency switcher outright once checkout has begun, forcing a return to cart to change currency · let both requests race with no cancellation, taking whichever resolves last.
- **Decision (3-5 bullets max):**
  - Chosen: cancellation-token-based race resolution — a currency switch cancels any in-flight step-entry quote; the current step re-enters and re-validates under the new currency.
  - Why: generalizes the platform's existing idempotent-submission discipline (`requirement-spec.md` §3.4's disable-until-response rule) to reads, without contradicting `localization.md`'s explicit design that currency and checkout progress are orthogonal (ruling out blocking) or reintroducing the exact staleness Domain Invariant #2 exists to prevent (ruling out an uncontrolled race).
  - Trade-off accepted: an extra round trip and brief step re-validation flicker on every mid-checkout currency change; the currency-restricted payment-method list can visibly narrow out from under a customer who already started selecting a method, until the newer quote resolves.
  - **Status: resolved, client-tier default.** No backend contract change implied — purely a client-side sequencing rule layered on two already-approved backend behaviors.

## Edge Case: Guest-Cart Merge Racing a Real-Time Inventory/Price Push

- **What happens:** a guest logs in, triggering Cart's own guest-to-authenticated merge; at the same moment, a live inventory/price push for a line item in the guest cart arrives before the merge response returns — the client's optimistic cart state and the just-fetched merge result can each reflect a different snapshot of the same item.
- **Why it happens:** `architecture.md`'s Real-Time Integration section documents one WS/SSE connection multiplexing cart-sync and inventory/price concurrently with any REST call, and `requirement-spec.md` §3.2 explicitly delegates merge-ordering entirely to Cart's own lifecycle — `kart-web` has no visibility into how merge's internal ordering relates to its own concurrently-arriving real-time events.
- **Solutions available (2):** treat the merge REST response as the sole authoritative snapshot post-login — suppress/buffer real-time cart-affecting events while the merge call is in flight, reconcile fully from the merge response, then resume normal consumption · apply real-time events and the merge response in strict arrival order with no special-casing.
- **Decision (3-5 bullets max):**
  - Chosen: suppress/buffer real-time cart-affecting events during the merge call's in-flight window; reconcile from the merge response, then resume.
  - Why: Domain/UX Invariant #1 requires the displayed cart to always reconcile with Cart's authoritative state and never invent client-only state — since merge itself produces authoritative state, treating it as a temporary sole source of truth avoids applying a stale real-time event on top of a cart the merge may have just restructured (item ids/counts can change during merge).
  - Trade-off accepted: any real-time price/stock change landing in this narrow window isn't reflected until the next event or reconnect — a small, self-resolving staleness window.
  - **Status: final.** Purely a client sequencing rule; no backend contract change needed.

## Edge Case: Self-Service Return Auto-Approval Racing a Chargeback on the Same Order

- **What happens:** a customer submits a return/refund request that qualifies for `checkout-and-refunds.md` §B.4's auto-approval fast path at nearly the same time the card network delivers a chargeback against the same order — both are independent triggers that can each end with money being returned against the same order.
- **Why it happens:** `checkout-and-refunds.md` §B.4/B.5 defines the auto-approval path calling `POST /payments/{id}/refund` under a system principal with no documented check against an in-flight or just-landed chargeback, while `kart-order-service/edge-cases.md`'s "Chargeback Received Against an Order in Any Post-Payment State" independently drives the order straight to `Refunded` from any post-`Paid` state — the two flows were designed in separate documents with no cross-reference to each other.
- **Solutions available (3):** `kart-web` re-fetches `GET /orders/{id}` immediately before submitting the return request and blocks submission (directing the customer to Support) if the order is already `Refunded` or chargeback-flagged, rather than trusting last-rendered state · submit regardless and rely entirely on `kart-payment-service`'s `SUM(refunds.amount) <= captured_amount` constraint to reject a second refund server-side · do nothing client-side, treating this purely as a backend-service concern outside `kart-web`'s scope.
- **Decision (3-5 bullets max):**
  - Chosen: both — a fresh state check immediately before submission for UX (option 1), with the payment-service constraint (option 2) as the authoritative guard; option 3 alone is rejected. **Precedence rule, now fixed:** a chargeback always wins over a customer-initiated auto-approval when both target the same order — `kart-payment-service/requirement-spec.md` §4's existing domain invariant ("a `payment_intent` marked `disputed` must reject any new refund attempt until the dispute is resolved") already forces this outcome mechanically: a chargeback landing first or within the same narrow window marks the intent `disputed`, and the auto-approval's own `POST /payments/{id}/refund` call is rejected by that pre-existing guard, not a new mechanism.
  - Why: `architecture.md`'s Boundary Rationale is explicit that every client-side check is "UX convenience, never the actual boundary" — the fresh state check (option 1) closes the common-case UX (a customer sees "this order is already refunded," not a raw error), while the already-approved Payment invariant (option 2, not new scope) closes the actual race regardless of timing; a bank-initiated dispute is treated as authoritative over a customer's own request because the customer no longer controls the funds once a chargeback lands — the same reasoning `kart-order-service/ddd-model.md` already applies to reaching `Refunded` "from any state `Paid` onward, since a bank-initiated dispute is not gated on Order's own internal state."
  - Trade-off accepted: on rejection, `kart-web` must map the `disputed`-conflict response to a specific, non-generic UI state ("this order has an active dispute — contact Support") rather than a generic failure — captured as a ticket alongside the `ReturnRequest` sub-resource itself (`tickets.md`), not a new invariant to design.
  - **Status: resolved, final.** No new backend mechanism required — `kart-payment-service`'s existing `disputed`-guard already makes chargeback-precedence the enforced outcome; this client-tier decision only fixes the resulting UI behavior and confirms the precedence rule explicitly so it isn't re-litigated.

## Edge Case: Cookie-Consent-Version Bump Arriving Mid-Session With Analytics Already Loaded

- **What happens:** a customer consented under `consentVersion` N and analytics/marketing scripts are already running client-side; an ops-triggered `consentVersion` bump (e.g. a new marketing sub-processor added) takes effect later in the same, uninterrupted browsing session — but `privacy.md` §A.4 only states the banner "re-shows on next visit," with no defined mid-session check.
- **Why it happens:** `kart-web` is a long-lived SPA post-hydration (`seo.md`'s whole hydration model) — a customer can browse an entire session across many client-side route changes without a single fresh SSR response, so "next visit" as literally written means "next time the tab is closed and reopened," a materially longer exposure window than the wording implies, with no mechanism (unlike `security.md`'s BroadcastChannel session sync) for an already-running tab to learn of the version bump.
- **Solutions available (3):** leave as designed — staleness checked only at the next fresh SSR page load (`privacy.md` §A.2's "rendered SSR'd on kart-web's first response") · check `consentVersion` on every client-side route navigation (Angular Router event), re-showing the banner in-session the moment a mismatch is detected, no reload required · push the new `consentVersion` over the existing real-time WS/SSE connection as a new message type, triggering an immediate in-session banner re-show.
- **Decision (3-5 bullets max):**
  - Chosen: check `consentVersion` on every client-side route navigation, not only on a fresh SSR page load.
  - Why: this is a low-cost addition reusing an event Angular already fires (the cached config value is already fetched at boot), versus option 3's new real-time message type for a non-domain concern this doc set never establishes elsewhere, and versus option 1's practical exposure window being far longer than `privacy.md`'s own wording suggests for a single-page-app session.
  - Trade-off accepted: a customer who lands on one page and never navigates again within the session (e.g., single PDP visit ending in tab-close) still won't see the updated banner until their next visit — this narrows but doesn't fully close the gap.
  - **Status: resolved as a client-tier default**, tightening `privacy.md` §A.4's "next visit" to include "next in-app navigation." Recorded here since `privacy.md` itself doesn't yet state this explicitly — worth folding back into that doc in a future revision, not blocking.

## Edge Case: GDPR Erasure Submitted While an Authenticated Session Is Open in Another Tab

- **What happens:** a customer submits "Delete my account" (`privacy.md` §B.5) from one tab; erasure processing begins asynchronously (fans out to `UserDataErased` consumers) while a second tab, already open and authenticated, retains a valid session and can still submit mutating requests during the window between erasure-request acceptance and the eventual session/token-family revocation actually completing.
- **Why it happens:** `privacy.md` §B.5 reuses ADR-0016/0017's fan-out mechanism "end-to-end" — token-family revocation at `kart-identity-service` is one of many async `UserDataErased` consumers, so a window necessarily exists between request acceptance and revocation; `security.md`'s `BroadcastChannel('kart-session')` sync only fires on an explicit logout action today, not on an erasure request, so it doesn't cover this case as currently scoped.
- **Solutions available (3):** on successful erasure submission, `kart-web` proactively triggers the same client-side logout+broadcast it uses for "log out everywhere" (invalidate the local BFF session, broadcast over the existing `BroadcastChannel('kart-session')`) immediately, ahead of the async backend fan-out reaching Identity · do nothing extra client-side — rely purely on the backend's own eventual token-family revocation, accepting the fan-out's natural latency as the exposure window · block the erasure confirmation UI until a synchronous "all sessions revoked" acknowledgment returns, turning the async platform-wide fan-out into a synchronous customer-facing wait.
- **Decision (3-5 bullets max):**
  - Chosen: immediate client-triggered logout+broadcast on erasure submission, layered on top of (not replacing) the backend's own eventual revocation.
  - Why: `security.md`'s existing `BroadcastChannel` mechanism already exists precisely to close every other authenticated tab instantly, for exactly this class of problem ("prevents a stale-authenticated tab from submitting a mutating request after the user believed they'd logged out elsewhere") — erasure is a strictly stronger case of that same problem, so reusing the identical mechanism closes the client-visible window immediately without inventing option 3's new synchronous backend contract.
  - Trade-off accepted: this only closes the window for tabs/devices where `kart-web` is actively running to receive the broadcast — a device offline at the moment of erasure still relies solely on the backend's eventual token-family revocation to actually end its session, unchanged from before this decision.
  - **Status: final for the client-tier mitigation.** The underlying backend fan-out timing is `kart-identity-service`/ADR-0016's own concern, unaffected by this decision.

## Edge Case: PWA Offline-Queued Add-to-Cart Replaying Against Stale Price/Stock

- **What happens:** a customer offline adds an item to cart (permitted to queue per Domain/UX Invariant #3); by the time connectivity returns and the queued mutation replays against `kart-cart-service`, the item's price has changed or stock is exhausted — the mutation was accepted as "safe to queue" when made, but replays at an unconfirmed price/availability.
- **Why it happens:** `requirement-spec.md` §2/§8.3 draws the offline-queueing line at add-to-cart/wishlist being safe to queue while place-order/submit-payment are not, reasoning that a queued payment against a "possibly-changed cart/price" is unsafe (Invariants #2/#3) — but the same staleness risk exists, at smaller stakes, for a queued add-to-cart, and neither the requirement-spec nor the PWA decision states what happens to displayed price/quantity once a queued mutation actually lands.
- **Solutions available (3):** replay the queued mutation as SKU+quantity only (never a frozen price), immediately re-running the existing live re-quote/stock-check on landing and surfacing any difference via the standard toast/snackbar pattern (§3.7) rather than a silent success · queue the mutation with its perceived-at-add-time price/stock frozen into the payload, trusting the server to reject/adjust and showing whatever error comes back verbatim · refuse to queue add-to-cart at all once offline beyond some threshold, narrowing Invariant #3's carve-out further than the requirement-spec currently states.
- **Decision (3-5 bullets max):**
  - Chosen: replay as SKU+quantity only; the existing live re-quote/stock-check flow (already mandatory at cart/checkout per Domain Invariant #2) runs immediately on landing, with an explicit toast if the result differs from what the customer saw offline.
  - Why: a direct extension of Domain Invariants #2 and #4 to the offline-replay moment specifically — it needs no new backend capability since re-quote-on-cart-view is already mandatory elsewhere, and it avoids the "fabricated client-side number" failure mode the no-dark-patterns invariant (§8.5) already forbids, which a frozen-price replay (option 2) risks implying.
  - Trade-off accepted: a customer whose queued add-to-cart replays into "now out of stock" gets a worse in-the-moment experience than offline (where the app couldn't have known) — but this is strictly better than a phantom successful add discovered wrong only at checkout, which Invariant #2 already treats as the worse failure.
  - **Status: final.** A non-negotiable extension of Domain Invariants #2/#4 to the offline-replay case, not a new open question.

## Edge Case: Deferred-Hydration Widget Consuming a TransferState Value Aged Out Before Its Trigger Fires

- **What happens:** a below-the-fold widget (recommendation carousel, review list) is `@defer`'d with a `hydrate on viewport`/`interaction` trigger; its data was fetched at SSR time and serialized via TransferState. If the customer takes a long time to scroll to or interact with that section, the widget hydrates using data that's now materially old — a since-moderated-out review still rendered as published, or a "customers also bought" recommendation for an item that's since sold out.
- **Why it happens:** `seo.md` §10 explicitly excludes only "live inventory count, live price" from TransferState reuse; it does not exclude recommendation/review/promotion payloads, and §9's lazy-hydration triggers have no time bound — a deferred block can sit unhydrated for an arbitrary wall-clock duration after the SSR response was generated, since nothing gates how long a customer takes to scroll or interact.
- **Solutions available (3):** attach a max-age to every TransferState-carried payload feeding a `@defer` block, forcing a fresh fetch if the trigger fires after that age elapses · exclude all `@defer`-gated widget data from TransferState entirely, always fetching fresh the moment the trigger fires (treat every deferred block like the already-excluded live-price/inventory case) · leave as-is, accepting stale deferred content for the widget categories `seo.md` already classifies as non-LCP-critical/lower-stakes.
- **Decision (3-5 bullets max):**
  - Chosen: exclude all `@defer`-gated widget data from TransferState reuse; always fetch fresh at trigger time.
  - Why: a direct generalization of the same rule `seo.md` §10 already establishes for a different reason — don't trust a transferred value once the point of use is decoupled in time from the point of fetch — rather than inventing a new per-data-type max-age policy (option 1) with no existing number to anchor it to; a moderated-out review shown as still-published is specifically a moderation-bypass against `requirement-spec.md` §3.1's "moderation-aware" review-display requirement, so option 3 (accept staleness) doesn't hold for reviews even if it might for cosmetic recommendation staleness.
  - Trade-off accepted: gives up TransferState's no-second-fetch benefit specifically for deferred widgets — an extra round trip exactly when a customer scrolls to or interacts with a recommendation/review/promo block. Bounded cost, since these are by definition the non-LCP-critical parts of the page.
  - **Status: resolved as a client-tier default**, extending `seo.md` §10's existing exclusion rule; worth folding back into that doc explicitly in a future revision, not blocking.

## Edge Case: Feature Flag Flips ON in Production While a Tab Is Already Open With Old Cached Code

- **What happens:** a `🚧`-gated feature's Unleash flag flips OFF→ON in Production (`api-strategy.md` §4/§8 stage 4 "GA") while a customer already has `kart-web` open in a tab from before the flip — that tab's already-loaded bundle/lazy chunk/flag-value cache reflects the pre-flip state, so the same session can see the feature as "coming soon" in the stale tab and live in a freshly opened one.
- **Why it happens:** `api-strategy.md` §4 states pipeline-stage-driven default states but not how an already-running SPA instance learns of a flag change — `kart-web`'s architecture is SSR + hydration then long-lived client-side routing (`seo.md`), so an open tab is exactly the kind of already-hydrated, already-bundled session a server-side-only flag flip has no built-in channel to reach.
- **Solutions available (3):** resolve the flag value once at SSR/bootstrap time and never re-check it for the tab's lifetime — a flip takes effect for a given customer only on their next full/navigation-triggered SSR response · poll the flag-evaluation endpoint (or subscribe over the existing real-time channel) and hot-swap feature availability mid-session, including dynamically importing the previously-unloaded feature module · force a one-time hard reload of any open tab the instant a flag relevant to its current route flips, pushed over the real-time channel.
- **Decision (3-5 bullets max):**
  - Chosen: resolve flag value once per SSR bootstrap/session; a flip's effect on an already-open tab is deferred to that tab's next navigation-triggered SSR response or full reload.
  - Why: matches this app's existing architecture directly — `api-strategy.md`'s four-stage lifecycle treats a GA flip as the end of a soak/rollout process, not an instant customer-facing cutover; options 2 and 3 require new infrastructure (a flag-push channel, dynamic module loading for a session that never bundled the module) that nothing else in this doc set establishes, for a feature category that by definition isn't safety- or money-critical enough to justify that investment — unlike the order/checkout real-time channels, which get it specifically because Domain Invariant #2 demands it.
  - Trade-off accepted: two open tabs of the same session can show inconsistent feature availability for as long as the older tab stays open without navigating — judged acceptable because the underlying change (a feature going GA) carries no correctness/money risk, unlike the real-time-tracked domain data (cart, price, stock, order status) this doc's other edge cases hold to a much tighter bar.
  - **Status: final.** A client-tier engineering default consistent with `api-strategy.md`'s existing lifecycle model; no backend or infra change implied.
