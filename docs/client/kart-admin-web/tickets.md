## Flagged Gaps — Not Decomposed Into Tickets (would invent scope, not decompose it)

- **The `@kart/design-system` package/repo itself is out of scope for this ticket list.** `../design-system.md` fixes it as its own repo (`kart-design-system`), "phased alongside Phase 4 (Client Applications) since neither client app can consume it before it exists" — every ticket above that references a shared component (Access Denied empty-state, data-table primitives, modal shell) *consumes* that package, it doesn't build it. No ticket here builds `@kart/design-system` itself.
- **WS/SSE real-time push for the Refund Requests queue or the audit/action feed** — `architecture.md` Dependencies table marks it explicitly optional at launch ("add only when a concrete workflow needs it"); `edge-cases.md`'s "Concurrent Support Agents Double-Approving" resolution and `design-decisions.md`'s "Refund Request Approval" decision both explicitly reject standing up this infrastructure for the current scope. No ticket until a concrete workflow forces it.
- **A `SharedWorker`-based single leader-election session coordinator** — considered and rejected in `design-decisions.md`'s "Multi-Tab Session Sync" decision in favor of the simpler `BroadcastChannel` approach already covered by AUTH-3. No ticket.
- **A grant-change propagation channel (extending `BroadcastChannel('kart-admin-session')` to carry permission/grant-change events)** — `edge-cases.md`'s "Multi-Tab BroadcastChannel Doesn't Propagate a Mid-Session Grant/Role Change" explicitly resolves to leave the channel session-lifecycle-scoped only, relying on server-side enforcement instead. No ticket.
- **PWA/offline support and active multi-locale i18n build-out** — `requirement-spec.md` §2 marks both "not required"/"structurally ready but not actively built" for this internal tool at launch. No ticket until a concrete field-support-offline or multi-locale back-office scenario is named.
- **`kart-order-service`'s own formalization of the `ReturnRequest` child aggregate** (state machine, table, event) — `../kart-web/checkout-and-refunds.md` §B.4 itself says this is "captured as a ticket (`tickets.md`), not invented wholesale in this client-tier doc," and that ticket belongs to `kart-order-service`'s own ticket list (a backend service concern), not this app's. SUP-3/SUP-4 above consume that aggregate's eventual API; they don't define it.
- **The new "Rejected" customer-notification trigger** (`../kart-web/checkout-and-refunds.md` §B.6: "a new notification... captured as a ticket, since today's event catalog has no rejection-notice trigger") is Notification Service/`kart-order-service` backend scope, not a `kart-admin-web` ticket — SUP-4 only calls the existing reject action; the notification fan-out it triggers is implemented elsewhere.
- **Final response shape of `kart-admin-service`'s own admin-write endpoints** this app's screens call (CAT-1 through IDN-2) is that service's own API Design Agent's job, not this app's — each ticket above is this app's best-effort consumer of an already-specified or soon-to-be-specified contract, not the definer of it.

## Notes for Sprint Planner Agent

- **AUTH-3 (idle-session state machine) is the single shared foundation**, analogous to `kart-admin-service/tickets.md`'s ADM-1 — every feature ticket in `catalog-management`, `order-exceptions`, `support-console`, `identity-admin`, and two of three `audit-compliance` tickets depend on it directly for session/role context (the interceptor that attaches the session cookie, the tab-active flag the silent-refresh interceptor reads, and the role claim every route guard reads). Build AUTH-1 and AUTH-2 (the two login flows) first and in parallel — they're mutually independent — then AUTH-3 immediately after both land, since it needs a working session from either login path to have anything to manage. AUTH-4 and AUTH-5 both depend only on AUTH-3, not on each other, and can proceed in parallel once it lands.
- **AUTH-5 (category-grant UI gating) is the second shared foundation** nearly every write-capable feature ticket needs (all of `catalog-management`, all of `identity-admin`, `order-exceptions`, `support-console`, and AUD-3). AUD-1 and AUD-2 are the two exceptions — `AdminActionPerformed`'s audit viewer is a coarse role gate only, no per-category grant check applies (`kart-admin-service/api-contract.yaml`'s own note on `GET /admin/actions`), and the analytics dashboards similarly read from `kart-analytics-service`'s `InternalBI` path rather than a category-gated admin-write endpoint — so both can start as soon as AUTH-3 lands, without waiting on AUTH-5.
- **Once AUTH-3 and AUTH-5 land, the four `catalog-management` tickets (CAT-1 through CAT-4), the two `identity-admin` tickets (IDN-1, IDN-2), `order-exceptions`' ORD-1, `support-console`'s SUP-1/SUP-2/SUP-3, and `audit-compliance`'s AUD-1/AUD-2 are all mutually independent and can be parallelized freely across engineers** — the same "no intra-app create-before-update chain" reasoning `kart-admin-service/tickets.md` applies to its own business-category tickets holds here too, since each screen is a thin proxy to a different owning backend service/endpoint, not a dependency on a sibling screen in this app.
- **Sequencing pairs that are hard dependencies, not just recommendations:** ORD-2 (fulfillment-exception resolution) needs ORD-1 (order lookup/detail) built first, since the exception-resolution action is reached from an order's own detail view. SUP-4 (Refund Request Approve/Reject) needs SUP-3 (the queue list/detail) built first for the same reason. AUD-3 (Privacy Requests) needs AUD-1 (the parent Audit & Compliance screen it nests inside) plus AUTH-5 (the sub-view-granularity render-time check it reuses) plus **XTEAM-1** — the `compliance` grant value must exist in `kart-admin-service`'s own enum before this app can request or receive it in a grant/session payload.
- **XTEAM-1 is a cross-repo coordination item, not something this app's own engineers can close unilaterally.** File it against `kart-admin-service`'s own backlog (it amends that service's existing ADM-1 ticket/schema, not a new aggregate there) and treat it as an external blocking dependency for AUD-3 only — no other ticket in this list touches the `compliance` value. Per `edge-cases.md`'s own closing note, this is "no new mechanism, no blocking policy dependency" once merged — genuinely small backend scope, but it still gates AUD-3's own start date.
- **IDN-2's category dropdown must be built enum-driven (reading `kart-admin-service`'s `GrantCategory` list), not with the four-then-five values hardcoded**, specifically so XTEAM-1 landing doesn't force a second follow-up PR to this screen — flagged directly in IDN-2's own row above, repeated here because it's an easy-to-miss implementation detail that determines whether AUD-3's dependency on XTEAM-1 is clean or requires reopening IDN-2.
- **Recommend building this app only after `kart-admin-service`'s own corresponding tickets (`kart-admin-service/tickets.md` ADM-1 through ADM-16) are stable and deployed**, the same "consumer app follows its backend service" ordering `docs/services/README.md`'s "Recommended Build Order" already establishes platform-wide — CAT-1/2/3/4, IDN-1/2, and AUD-1 each call a specific ADM-* endpoint by number (cited in their own Design Source column above) and cannot be meaningfully integration-tested before that endpoint exists.
- No circular dependencies in this graph. The longest path is 4 deep: AUTH-1/AUTH-2 → AUTH-3 → AUTH-5 → AUD-3 → (XTEAM-1, external).
